# Dinero — хендофф для следующего этапа (MVP → полноценное приложение)

Снимок состояния на коммит `f336e2a` (10 коммитов, `main`, не запушено —
`origin` настроен на `https://github.com/pozich/dinero`). Это не план
развития и не ТЗ — фактическое описание того, что уже есть, как оно
устроено и почему, плюс список того, что сознательно не сделано. Пишу
это, чтобы в новом чате можно было сразу продолжать, не перечитывая код
и git log.

Источники правды в репозитории: `SPEC.md` (все решения по `[РЕШЕНО]`
помечены прямо в тексте, с обоснованием) и `CLAUDE.md` (правила работы:
не трогать `samples/`, суммы — целые тиыны, коммиты `feat|fix|refactor|
chore(scope): …`, один логический шаг = один коммит).

## 1. Что это за приложение

Локальный (офлайн, без аккаунтов) учёт личных финансов по банковским
выпискам: пользователь кидает PDF-выписки → приложение детерминированно
(без нейросети) режет их на операции, склеивает в одну БД без дублей,
находит переводы между своими счетами → пользователь сам раскидывает
операции по категориям, по возможности только с клавиатуры. Заменяет
предыдущий пайплайн python-скрипт → CSV → Obsidian.

Платформы: Linux (Arch/Hyprland, основная среда разработки), Windows 11,
Android 15. Одна кодовая база (Tauri 2).

## 2. Стек и ключевые архитектурные решения

- **Tauri 2 + React 19 + TypeScript + Vite.** SQLite через
  `tauri-plugin-sql` (sqlx), суммы — целые **тиыны** (int), никаких float.
- **Хранилище — vault, как в Obsidian** (`src-tauri/src/vault.rs`): при
  первом запуске выбирается папка на диске (по умолчанию тихо, без
  диалога — см. гочу #1 ниже), в ней лежит `dinero.db`. Путь к папке
  хранится отдельно в `~/.config/dinero/vault.json`. Пользователь сам
  синхронизирует эту папку через Syncthing — приложение синхронизацию не
  делает. **Важный и не чинится малой кровью риск:** SQLite — один
  бинарный файл, Syncthing конфликты не мержит; открывать Dinero
  одновременно на двух устройствах с одним vault'ом нельзя.
- **Парсинг — строго детерминированный**, без нейросетей, по
  координатам текста в PDF (`pdfjs-dist`), а не по регекспам над плоской
  строкой — так надёжнее для банков с ломаной вёрсткой (см. Eurasian
  ниже). Общая утилита `src/parsers/pdfRows.ts` группирует текстовые
  фрагменты pdf.js в строки/колонки по координатам; каждый банк — свой
  модуль поверх неё.
- **Golden-тесты**: каждый парсер проверяется на реальных файлах из
  `samples/` (в `.gitignore`, не коммитятся) двумя независимыми
  источниками чисел — итоговым блоком из самой выписки и суммой всех
  распознанных строк — и оба должны сойтись до копейки. Если выписка не
  сходится при реальном импорте — импорт отменяется целиком (п.6.1
  SPEC.md), ничего не пишется в БД наполовину.
- **Дедупликация**: хэш всего файла (повторный импорт того же файла —
  no-op) + построчный ключ (счёт, дата, сумма, описание, порядковый номер
  повтора в этот день) для перекрывающихся файлов — две одинаковые
  операции в один день не считаются дублями.
- **Категории — дерево** (`parent_id`, пока не используется в UI
  глубже одного уровня, но заложено в схеме).
- **Миграции** — свой простой список (`Migration{version, sql}`) через
  встроенный механизм `tauri-plugin-sql` (`add_migrations`), НЕ
  самописный раннер — он там уже есть из коробки, просто плохо
  задокументирован.

## 3. Модель данных (`src-tauri/migrations/`)

`0001_init.sql`:
- `accounts` — 7 строк, засеяны миграцией: `kaspi_gold`, `halyk_salary`,
  `halyk_standard`, `eurasian`, `bcc` (два последних — транзитные,
  `is_transit=1`), `cash`, `kaspi_deposit` (два последних — виртуальные,
  без своего файла-источника).
- `statements` — загруженный файл: банк, период, `file_hash` (UNIQUE,
  дедуп), имя файла.
- `transactions` — счёт, дата (ISO, время есть только у Eurasian, у
  остальных `00:00:00`), сумма в тиынах со знаком, описание, `raw_type`,
  `dedup_key` (UNIQUE), `related_transaction_id` (nullable — используется
  только для привязки комиссии брокера к её операции на Halyk
  «Стандарт», это НЕ то же самое, что `transfer_links`).
- `categories` — дерево (`parent_id` nullable), `is_system` (сидированы
  «Инвестиции» и «Внутреннее»).
- `splits` — разрез операции на несколько категорий; сумма частей обязана
  совпадать с суммой операции (проверяется в
  `src/db/transactions.ts::setTransactionSplits`).
- `transfer_links` — связь двух операций «ушло со счёта A ↔ пришло на
  счёт B», `confirmed` (1 — для однозначных случаев вроде Kaspi Deposit и
  переноса наличных, см. ниже; для «обычных» межбанковских переводов
  UI подтверждения **не построен**, см. раздел 5).

`0002_category_rules.sql`:
- `category_rules` — правила авто-категоризации: `pattern` (regex),
  `case_sensitive`, `category_id`, `priority` (меньше = раньше
  проверяется, первое совпадение побеждает), `is_active`.

## 4. Что реализовано и протестировано

62 теста (`npm test`), часть — против реальных файлов из `samples/`
(пропускаются если папки нет), часть — против настоящей SQLite через
`node:sqlite` (`tests/testDb.ts` накатывает все миграции по-настоящему,
не моки).

**Парсеры** (`src/parsers/`) — все 4 банка, с golden-числами,
независимо перепроверенными:

| Банк | Файлы-примеры | Особенность парсинга |
|---|---|---|
| Kaspi Gold | 4 годовых файла | Первая страница — справка, пропускается. Многострочный тип («Receipt from your account»/«Transfer to your account» + «account» на следующей строке). Валютная под-строка в скобках — не новая операция. |
| Halyk (оба счёта) | 1 файл «Зарплата», 1 «Стандарт» | Один парсер, тип счёта определяется по строке «Тип счета» в самом файле. Сумма берётся из «Приход/Расход в валюте счёта», НЕ из «Сумма операции» (может быть в USD). Комиссия брокера — отдельная связанная транзакция (`related_transaction_id`). Многотраншевые продажи акций — несколько строк с одним «Номер заявки», НЕ склеиваются. |
| Eurasian | 2 файла | Самый хрупкий формат: PDF ломает лигатуру «ti» в случайных местах (`Transac\u0000on`), парсинг идёт строго по x-координате колонки, не по словам. Одна операция — 2-3 физические строки, может рваться через разрыв страницы. |
| BCC | 1 файл | Самый простой: построчно, дата `ДД.ММ.ГГ`, сумма с точкой. |

**Импорт** (`src/import/`): `detectBank.ts` определяет банк по BIC в
тексте первой страницы (не по имени файла). `importStatement.ts`
оркестрирует: хэш файла → golden-проверка → запись в БД с дедупом по
строкам → для Kaspi Gold и Halyk дополнительно синтезирует зеркальные
операции:
- **Kaspi Deposit** (`src/parsers/kaspiDeposit.ts`): строка «Receipt from
  your account / From Kaspi Deposit» (и обратная) зеркалится на
  виртуальный счёт `kaspi_deposit` + однозначный `transfer_links`
  (`confirmed=1`), без эвристики по дате/сумме — связь ясна из текста.
- **Наличные** (`src/parsers/cashMirror.ts`): снятие в банкомате
  (Halyk «Снятие денег без карты…») и пополнение картой наличными
  зеркалится на `cash`. Для Kaspi дополнительно считаю
  `Replenishment`/«At Kaspi ATM» внесением наличных — **это моя
  экстраполяция** правила «внесение в банкомат — наоборот» из SPEC.md,
  в самой спеке такого примера не было, в реальных файлах — было
  (несколько раз), и подтверждено логикой, но стоит перепроверить, если
  найдутся новые банкоматные паттерны.

**Переводы между счетами** (`src/transfers/matchTransfers.ts`):
алгоритм поиска кандидатов (сумма+знак+разница дат ≤3 дня + бонус за
упоминание банка-контрагента в описании) — **чистая функция, которая
только предлагает кандидатов**. Проверено на реальных пересекающихся
выписках — находит все 5 документированных в SPEC.md примеров (таблица
4.3). **UI для подтверждения и записи `transfer_links` НЕ построен** —
это главный недостающий кусок, см. раздел 5.

**Импорт → БД → экран операций**: полный цикл работает. Таблица
операций с датой «Oct 25» (год — если на экране несколько лет),
клавиатурная категоризация (↑/↓ выбор строки → Enter → ввод категории
с автодополнением и созданием новой → Enter сохраняет и переходит
дальше), Ctrl+S — окно разреза на несколько категорий, «применить ко
всем с таким же описанием» — окно со списком и галочками. Фильтры
(поиск, счёт, период, «без категории»), сортировка по нескольким
колонкам с приоритетом.

**Правила авто-категоризации** (`src/features/operations/RulesDialog.tsx`,
`categoryRuleMatch.ts`): regex по описанию → категория, применяются
**только по кнопке «Применить правила»** с окном-превью и галочками,
никогда автоматически. Это сверх исходного MVP, добавлено отдельным
запросом пользователя после Э7 (SPEC.md п.6.4a) — специально НЕ путать
с «автокатегоризацией и нейросетью», исключённой из MVP в п.7: тут всё
детерминированное и задаётся самим пользователем.

**Экран файлов**: карточки-чеки (банк/период/число операций — именно из
файла, без учёта зеркальных операций на других счетах), 3D-переворот
при наведении → «Заменить»/«Удалить» с подтверждением и предупреждением,
если у операций уже есть категория. Удаление чистит splits/
transfer_links/транзакции (включая комиссии и зеркала).

**Платформы**: адаптив (нижняя навигация и крупные тач-зоны ниже 768px,
подсказки про горячие клавиши скрыты), реальный debug APK собран и
проверен на этой машине (arm64), Windows — через GitHub Actions
(`.github/workflows/windows-build.yml`, собирает на настоящем
windows-раннере по тегу `v*`, ни разу не запускался).

## 5. Сознательно НЕ сделано / недоделано

Это не «не делать в MVP» из SPEC.md п.7 (графики, статистика, инвестиции,
облако, iOS — те исключены осознанно и останутся вне скоупа, если не
передумаете). Это именно **недостроенные куски** в рамках уже начатой
работы:

1. **Подтверждение переводов между счетами — нет UI.** Алгоритм в
   `matchTransfers.ts` находит кандидатов и покрыт тестами, но нигде в
   интерфейсе нельзя посмотреть список кандидатов и подтвердить/
   отклонить пару (что должно создавать `transfer_links` с
   `confirmed=1`, как у Kaspi Deposit). Сейчас межбанковские переводы
   просто остаются обычными операциями, которые пользователь должен
   сам заметить и вручную пометить какой-то категорией — это самый
   заметный разрыв между «собрано» и «удобно пользоваться».
2. **Экспорт CSV и экспорт/импорт БД — написаны, но отключены от UI.**
   Логика (`transactionsToCsv` и т.п.) была написана в Э6, но по ходу
   живой проверки пользователь решил, что это дублирует Syncthing+vault
   и не нужно прямо сейчас — код удалён из UI, но сам подход
   задокументирован в SPEC.md 6.6 («легко вернуть»). Если будет нужна
   выгрузка данных для внешнего анализа (раз нет графиков в
   приложении) — это первое, что стоит восстановить.
3. **Доходы/расходы нигде не считаются.** Нет ни одного места в UI, где
   видна сумма за период с учётом исключения переводов/инвестиций —
   прямое следствие пункта 7 SPEC.md («графики, дашборды — не в MVP»),
   но раз переводы всё равно не подтверждаются (см. п.1 выше), посчитать
   это сейчас было бы и технически невозможно корректно.
4. **Android: только debug-сборка, без релизной подписи.** Инструкция в
   README есть, ключ не генерировался. Сборка под все 4 архитектуры разом
   съедает ~19 ГБ в `target/` — собирайте по одной архитектуре
   (`--target aarch64`) для разработки.
5. **Windows-сборка никогда не запускалась и не проверялась.** CI
   настроен по образцу, но ни один релиз через него не собирался —
   возможны неожиданности (пути, иконки, NSIS-специфика).
6. **Правила категоризации — только regex по описанию.** Нет условий по
   сумме, счёту, диапазону дат — если понадобится более богатая
   фильтрация для правил, формат `category_rules` придётся расширять
   (сейчас это одно текстовое поле `pattern`).
7. **«Данные» вкладка** почти пустая — таблицы accounts/categories для
   отладки + путь к vault и кнопка его смены. Больше там ничего нет
   (не было задачи).
8. Бандл фронтенда не код-сплитится (`pdf.worker` ~2.4 МБ отдельным
   чанком, основной бандл ~750 КБ) — работает, но стоит внимания, если
   важен холодный старт на телефоне.

## 6. Технические грабли, на которые наступил (чтобы не наступать снова)

1. **pdfjs-dist в браузере требует `GlobalWorkerOptions.workerSrc`**,
   а в Node (тесты, `node:sqlite`) — нет, там свой fake-worker.
   Решение — ленивая настройка по окружению,
   `src/parsers/pdfjsWorker.ts::ensurePdfWorker()`, вызывается в начале
   каждого `parseXxx`/`detectBank`, no-op в Node.
2. **`tauri-plugin-sql`'s `sql:default` даёт только чтение**
   (select/load/close) — запись (`execute`) нужно разрешать отдельно,
   `sql:allow-execute` в `capabilities/default.json`. Без этого
   INSERT/UPDATE падает с «not allowed» только при реальном запуске —
   юнит-тесты (node:sqlite) эту проблему не ловят, это обнаружилось
   только при живой проверке в Tauri.
3. **Абсолютный путь в `sqlite:<path>` работает**, несмотря на то что
   документация плагина говорит «relative to BaseDirectory::App» — это
   потому что `PathBuf::push()` в Rust полностью заменяет базовый путь,
   если пушится абсолютный сегмент. На этом построен весь vault.
4. **Native-диалог (`rfd`) нельзя звать ДО старта окна Tauri** — поймал
   реальный краш («Failed to acquire ownership of main context») из-за
   двойной инициализации GTK-цикла на одном потоке. Решение: выбор vault
   на первом запуске — без диалога (тихий дефолт), смена папки — только
   из уже запущенного приложения через JS `@tauri-apps/plugin-dialog`.
5. **Сборка Android сразу под все 4 архитектуры разом** раздувает
   `target/` до ~19 ГБ и может уронить диск в 0 (бывало на этой
   машине) — всегда указывайте `--target <arch>` при разработке.
6. **Дедуп-ключи нужно считать батчем**, не по одной транзакции за раз:
   при поштучной вставке комиссий ordinal всегда сбрасывался в 1,
   из-за чего разные комиссии с одинаковой (дата,сумма,описание)
   схлопывались в дубликат и часть реально терялась — нашёл через тест
   на реальном файле Halyk «Стандарт» (36 комиссий вместо 41).
7. `Intl.NumberFormat` вставляет NON-BREAKING SPACE (U+00A0), не обычный
   пробел — если сравниваете форматированные суммы строкой, нормализуйте.

## 9. Ф1 (SPEC-2.md, раздел 2) — Надёжность данных [готово]

**Что сделано:**
- **journal_mode → DELETE.** `tauri-plugin-sql`/`sqlx` переключают БД в
  WAL при прогоне миграций (сохраняется в файле навсегда) — теперь первое
  же подключение (`src/db/client.ts`) переключает обратно одним PRAGMA, без
  изменений в Rust. Больше не будет `-wal`/`-shm` файлов в vault.
- **Lock-файл** (`src-tauri/src/lock.rs`) — `vault/dinero.lock`: устройство
  (`gethostname`), PID, время старта, heartbeat раз в минуту (отдельный
  `std::thread`, не async — не захотел тащить `tokio` как явную зависимость
  только для одного таймера). При старте: если старый lock свежий (моложе 5
  минут) — фронтенд показывает диалог «выйти / только чтение / всё равно
  открыть»; если протух — **забираем тихо, без вопроса** (SPEC-2.md
  формулирует это как «предложить забрать», но раз процесс гарантированно
  мёртв, спрашивать нечего — стоит проверить, что это ок). Закрытие окна
  (`WindowEvent::Destroyed`) освобождает lock.
- **Автобэкапы** (`src-tauri/src/backup.rs`) — копия `dinero.db` в
  `vault/backups/` при старте (не чаще раза в день) и перед импортом,
  удалением выписки, массовым применением категории, применением правил.
  Ротация — три независимые корзины (10 последних / 7 дневных / 4
  недельных), имя файла хранит причину и время, отдельной таблицы в БД
  нет — список бэкапов читается даже если сама БД не открывается.
  Восстановление **не** подменяет живое соединение — как и смена vault,
  просит перезапустить приложение. Экран «Данные» → раздел «Бэкапы».
- **Лог ошибок** (`src-tauri/src/logging.rs`) — `vault/logs/dinero.log`,
  ротация по размеру (1 МБ, 5 файлов). Только тип ошибки + место + опциональный
  id, никогда свободный текст — фронтенд (`src/reliability/errorLog.ts`)
  ловит `window.onerror`/`unhandledrejection` и пишет только `error.name` +
  координаты файла, никогда `.message`. Кнопка «Открыть папку логов» —
  экран «Данные» (через `tauri-plugin-opener`).
- **Детект sync-conflict файлов** — простая проверка подстроки
  `sync-conflict` в именах файлов корня vault, баннер сверху приложения.
- **Только чтение** — при выборе «только чтение» в диалоге блокировки
  отключаются: импорт/замена/удаление выписки (Файлы), вход в
  редактирование категории и клавиши Enter/Ctrl+S, кнопка «Применить
  правила» и форма правил (Операции). Кнопка «Изменить папку» на «Данные»
  **оставлена активной** — это не запись в БД, а только файл-указатель.
- **Undo/redo** (`src/undo/undoStack.ts`) — generic снимки «до/после» по
  строкам (не журнал команд, см. SPEC-2.md 2.3): Ctrl+Z/Ctrl+Shift+Z и
  кнопки ↶/↷ у шапки вкладок, глубина 50 шагов, только в памяти сессии.
  Подключено к: категории операции, разрезу, «применить к похожим»,
  CRUD и перестановке правил, «применить правила». Импорт и удаление
  выписки **не** через этот механизм — через восстановление бэкапа,
  как и было решено в плане Ф1.
- **Смоук-тест** (`e2e/`) — конфиг WebdriverIO + `tauri-driver`,
  `e2e/smoke.spec.mjs`: импорт (через тестовый хук `src/testHooks.ts` —
  WebDriver не может провести нативный диалог выбора файла) → категория →
  `reloadSession()` (это и есть «перезапуск» — tauri-driver убивает процесс
  и запускает новый) → категория на месте.

**Чего не хватает / риски:**
- **Смоук-тест так и не запускался — и на этой машине в принципе не может.**
  `tauri-driver` ставится без проблем (`cargo install tauri-driver`), но
  `WebKitWebDriver` **недостижим**: его нет ни в `webkit2gtk-4.1` из
  официальных репозиториев Arch, ни в AUR, ни в каком-либо
  Flatpak-окружении (проверено). Единственный путь — собрать webkit2gtk
  из исходников с `-DENABLE_WEBDRIVER=ON`, а свободного места на этой
  машине сейчас мало (9.6 ГБ на `/`, 3.4 ГБ на `/home`) — решили не
  рисковать и отложить прогон (пользователь выбрал «перейти к Ф2»).
  Гарнесс написан и типобезопасен, но **ни разу не прогонялся целиком**.
  На Windows для него нужен Microsoft Edge WebDriver версии, совпадающей
  с установленным Edge/WebView2 — там шансы выше.
  **Важный баг, который успели найти и починить при попытке запуска:**
  гарнесс по умолчанию целился в настоящий `~/.config/dinero/vault.json`
  — первый реальный прогон затронул бы боевую базу. Исправлено через
  `DINERO_CONFIG_DIR` (`src-tauri/src/vault.rs` + `e2e/wdio.conf.mjs`) —
  переопределяет и путь к файлу-указателю, и дефолтный vault, только
  когда переменная явно выставлена (сам тест создаёт временную папку).
- Первые Rust-тесты в проекте — `cargo test --lib` в `src-tauri/`, 3 теста
  на ротацию бэкапов (`src-tauri/src/backup.rs`), раньше тестов на Rust
  не было вообще, только vitest.
- Протухание lock-файла забирается автоматически без вопроса — отход от
  буквальной формулировки SPEC-2.md 2.1 («предложить забрать»), см. выше.
- `window.__dinero_e2e.importFile` — маленький, всегда присутствующий
  тестовый хук на `window` (не только в dev-сборке) — делает ровно то же,
  что кнопка импорта, с путём, который даёт вызывающий. Сознательный
  компромисс, не угроза безопасности (приложение полностью локальное), но
  стоит знать, что он там есть.

**Проверить руками:** лок-конфликт (запустить два экземпляра с одним
vault), восстановление бэкапа + перезапуск, Ctrl+Z на 10+ разных действиях
подряд, кнопка логов открывает папку.

## 10. Ф2 (SPEC-2.md, раздел 3) — Переводы, возвраты, импорт [готово]

**Схема:** `transfer_links` получила `status` (`pending`/`confirmed`/
`rejected` — см. п.9 выше, это было частью Ф1-чистки схемы, сделано
заранее) и `kind` (`transfer`/`refund`).

**Что сделано:**
- **`findRefundCandidates`** (`src/transfers/refundMatch.ts`) — тот же
  принцип, что `findTransferCandidates`: тот же счёт, нормализованное
  описание совпадает, возврат в тот же день или позже в пределах 14 дней,
  сумма возврата ≤ покупки. Проверено на реальных примерах: KOYEB
  (совпадает, confidence высокий) и **OZON сознательно НЕ совпадает** —
  его возврат (+13 485) больше покупки (−11 613), это и есть повод для
  ручной привязки, а не баг.
- **`src/db/transferLinks.ts`** — подтверждение/отклонение/разрыв связи.
  Важная тонкость: подтверждённая пара выкидывает **обе операции целиком**
  из будущих кандидатов (они уже решены), а отклонённая — выкидывает
  **только эту конкретную пару** (`pairKey`, порядко-независимый) — та же
  операция всё равно может предложиться с кем-то другим.
- **`src/review/buildReviewCandidates.ts`** — объединяет переводы и
  возвраты в один список, уже отфильтрованный от отклонённых пар;
  пересчитывается заново при каждом открытии/действии, ничего не хранит
  сам.
- **Экран «Проверить»** (`src/features/review/ReviewScreen.tsx`) —
  модальная панель, а не 4-я вкладка (SPEC.md п.8 держит шапку из трёх
  равных частей — посчитал, что добавлять четвёртую не стоило, раз
  можно обойтись счётчиком-кнопкой). Enter/Backspace/↑↓, ✓/✕ мышью.
  Кнопка-счётчик — в шапке приложения рядом с undo.
- **Ручная привязка** — правый клик по операции в «Операциях» →
  «Связать как перевод с…» (поиск, только операции с противоположным
  знаком) или «Разорвать связь», если уже подтверждена.
- Всё подтверждение/отклонение/разрыв — через undo-стек (это прямо
  указано в SPEC-2.md 2.3: «связывание переводов» должно откатываться
  Ctrl+Z).
- **Пакетный импорт** (`FilesScreen.tsx`) — выбор нескольких файлов,
  сортировка по периоду перед реальным импортом (`peekPeriod.ts` —
  облегчённый повторный разбор только ради даты периода, да, это
  повторная работа, но на небольшом числе файлов за раз это не важно),
  общий отчёт по каждому файлу + «Итого» + подсказка про найденные
  кандидаты в «Проверить».
- **Сообщение о расхождении golden-проверки** (`goldenMismatch.ts`)
  теперь показывает, какая именно проверка не сошлась и на сколько
  (в тенге). Локализация «в каком месяце/странице» из SPEC-2.md 3.3 —
  **не сделана**: ни один парсер сейчас не запоминает номер страницы или
  месяца при разборе, это честно оставлено как есть, а не притворно
  реализовано.

**Чего не хватает:**
- Долги (SPEC-2.md раздел 8) — панель «Проверить» и `transfer_links.kind`
  уже готовы принять третий вид (`debt`), но Ф7 ещё не начат.

  отчёт только подсказывает текстом, что нажать (см. выше, не стал

## 11. Ф3 (SPEC-2.md, раздел 4) — Ручные операции, категории, правила, экспорт [готово]

**Что сделано:**
- **Ручные операции** (`src/db/manualTransactions.ts`) — хоткей `N` и
  кнопка «+» (на телефоне — плавающая) открывают форму: счёт, приход/
  расход, сумма, дата, категория, заметка. `dedup_key` для них —
  `manual:<uuid>`, дубликаты разрешены (тот же принцип «два кофе — не
  дубль»). У импортированных операций в той же форме (правый клик →
  «Изменить») заблокированы сумма/дата/счёт/описание — редактируются
  только категория, заметка и «не учитывать» (db-слой это тоже
  проверяет, не только UI). Удалить можно только ручную.
- **Слияние при повторном импорте** (`src/import/mergeManualCandidates.ts`)
  — после импорта новые строки сверяются со всеми ручными операциями
  (тот же счёт, точная сумма, дата ±1 день); найденное показывается в
  окне «Это та же операция?», подтверждение переносит категорию/заметку
  на настоящую строку из выписки и убирает ручную.
- **Категории** (`src/db/categoryTree.ts`,
  `src/features/categories/CategoriesScreen.tsx`) — модальная панель с
  Данные: переименование (двойной клик), перенос через drag&drop (плюс
  зона «В корень»), слияние двух категорий, удаление с переназначением
  (на другую категорию или «без категории»), счётчики операций/суммы.
  Системные категории (Инвестиции, Внутреннее) защищены от слияния/
  удаления. Rename/move — через undo-стек; merge/delete — через бэкап
  (`bulk_action`), не через Ctrl+Z: могут задеть тысячи строк в `splits`,
  снимать их все в undo нецелесообразно.
- **Правила — доп. условия** (`src/features/operations/categoryRuleMatch.ts`)
  — счёт(а)/знак/диапазон суммы, все опциональны и объединяются с
  regex через И. Для живой проверки регулярки в `RulesDialog` используется
  отдельная чистая функция `testPattern` (только regex, без условий) —
  у неё нет настоящей операции для проверки счёта/знака/суммы, только
  пример текста. «Создать правило из этого» в окне «применить ко всем
  похожим» подставляет точный текст описания как regex и уже выбранную
  категорию.
- **CSV-экспорт** (`src/export/exportCsv.ts`) — дата, счёт, сумма,
  описание, категория полным путём, заметка, флаги; экспортирует то, что
  сейчас показано в таблице (с учётом фильтров). Пишет через новую
  команду `write_file_bytes` с UTF-8 BOM в начале файла — иначе Excel на
  Windows может показать кириллицу криво.

**Чего не хватает:**
- Долг/цель (поле из SPEC-2.md 4.2) не добавлено в схему — таблиц
  `debts`/`goals` ещё нет (Ф7/Ф9), добавится вместе с ними.
- Цвет/иконка категории (колонки есть) — ничем не используются, только
  заготовка под будущие графики.
- Условие «контрагент» в правилах — отложено до Ф7 (нужна сущность
  «Человек»), как и решили на этапе планирования.

**Проверить руками:** `N` → новая ручная операция на «Наличные» →
категория/заметка сохраняются; импорт выписки с операцией, похожей на
только что введённую руками → должно появиться окно «Это та же
операция?»; в «Категории» — перетащить одну категорию на другую,
слить две, удалить одну с переназначением; создать правило с условием
«только расход» и проверить «Применить правила»; «Экспорт CSV» и
открыть файл — кириллица должна быть читаемой.
