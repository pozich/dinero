# 03. Promise и `async`/`await`

Почти вся работа с базой данных и файлами в этом проекте — операции,
которые не завершаются мгновенно (чтение с диска, запрос к SQLite,
сетевой запрос). JS не умеет "подождать" блокирующе, как обычная
функция — он использует модель **Promise**.

## Проблема, которую решает Promise

Если бы `readFile` занимала время и возвращала результат как обычная
функция, программа бы "зависла", ожидая диск, и ничего больше не могла
бы делать (в том числе — отрисовывать интерфейс). Поэтому
долгие операции в JS не возвращают результат сразу — они возвращают
**обещание** результата (Promise), а дальше можно подписаться:
"когда будет готово — сделай вот что".

```ts
function delay(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

delay(1000).then(() => {
  console.log("прошла секунда");
});
console.log("это выведется СРАЗУ, до строки выше");
```

`Promise<void>` — обещание, у которого в итоге не будет полезного
значения (просто "готово/не готово"). `Promise<T>` — обещание значения
типа `T`. Так `findStatementByHash` возвращает `Promise<StatementRow | null>`
— "в итоге либо найденную строку, либо `null`, но не прямо сейчас".

## `.then()` — неудобно при цепочке

```ts
getDb()
  .then((db) => db.select("SELECT ..."))
  .then((rows) => rows[0])
  .then((row) => console.log(row));
```

Каждый следующий шаг — новый `.then()`, и обработка ошибок требует
отдельного `.catch()`. Это быстро превращается в "пирамиду". Поэтому
почти весь код проекта использует другой синтаксис для того же самого:

## `async`/`await` — то же самое, но читается как обычный код

```ts
async function run() {
  const db = await getDb();
  const rows = await db.select("SELECT ...");
  console.log(rows[0]);
}
```

Правила:
- `await` можно писать только внутри функции, помеченной `async`.
- `await promise` "разворачивает" Promise — код после этой строки не
  выполнится, пока промис не завершится, но *другой* код в программе
  (например, обработка клика) в это время продолжает работать как
  обычно — блокировки всего приложения не происходит.
- Функция, помеченная `async`, автоматически возвращает `Promise`, даже
  если внутри написано `return rows[0]` без явного Promise — TS сам
  оборачивает в `Promise<...>`.

Реальный, целиком настоящий пример (без упрощений):

```ts
// src/db/statements.ts:20
export async function findStatementByHash(
  db: DbClient,
  fileHash: string,
): Promise<StatementRow | null> {
  const rows = await db.select<StatementRow[]>(
    "SELECT * FROM statements WHERE file_hash = $1",
    [fileHash],
  );
  return rows[0] ?? null;
}
```

Разбор по строкам:
- `export async function findStatementByHash(...)` — функция
  асинхронная, значит её нельзя просто вызвать и получить `StatementRow | null`
  напрямую — вызывающий код обязан написать `await findStatementByHash(...)`.
- `db.select<StatementRow[]>(sql, params)` — сам SQL-запрос тоже
  асинхронный (ждём ответ от SQLite), поэтому и здесь `await`.
  `<StatementRow[]>` — generic-параметр (глава 02): "результат запроса —
  массив строк именно такой формы".
- `rows[0] ?? null` — если строка нашлась, вернуть её, если массив
  пустой (`rows[0]` будет `undefined`) — вернуть `null` явно, а не
  `undefined` (сигнатура обещает именно `StatementRow | null`).

## Ошибки: `try`/`catch`

Если промис "отклоняется" (reject) — например, SQL-запрос упал из-за
нарушения ограничения (foreign key, см. главу 07) — непойманная ошибка
"вылетает" туда, откуда вызвали `await`. Чтобы обработать:

```ts
try {
  await deleteStatement(db, statement.id);
  setReport(["удалено"]);
} catch (e) {
  setReport([`не удалось удалить (${e instanceof Error ? e.message : String(e)})`]);
} finally {
  setBusy(false);
}
```

(это реальная, чуть сокращённая версия `confirmPending` из
`src/features/files/FilesScreen.tsx`) — `finally` выполняется в любом
случае, и успех, и ошибка, поэтому в него кладут "обязательную
уборку" (здесь — снять флаг "идёт операция").

**Важная практическая деталь**, которая реально ломала этот проект:
если `catch` не написан вообще, а промис отклонился — ошибка не
появляется на экране никак. Она становится "unhandled promise
rejection" — тихо падает в консоль разработчика, а пользователь видит
только то, что "кнопка как будто не сработала". Именно так выглядел
баг "удалить/заменить файл не работает" в этом проекте: у
`deleteStatement` внутри падала ошибка нарушения внешнего ключа (см.
главу 07), а `confirmPending` не имел `catch` — ошибка просто
исчезала.

## `Promise.all` — несколько операций параллельно

Если несколько промисов не зависят друг от друга, ждать их по очереди
(`await a(); await b();`) медленнее, чем запустить сразу оба и ждать
обоих вместе:

```ts
// src/features/data/DataScreen.tsx (сокращено)
const [debts, repayments, people] = await Promise.all([
  listDebts(db),
  listRepayments(db),
  listPeople(db),
]);
```

Все три запроса к базе уходят одновременно, а не один за другим —
`Promise.all` ждёт, когда ВСЕ завершатся, и возвращает массив
результатов в том же порядке, в котором передали промисы.

## Итог главы

Теперь сигнатуры вида `function x(...): Promise<Y>` читаются как «эта
операция не мгновенная, у вызывающего кода обязан быть `await`», а
отсутствие `catch` — не мелочь, а реальная причина "кнопка не
работает" без единой видимой ошибки.
