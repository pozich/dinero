# 08. Tauri: окно, Rust-процесс, граница invoke()

Tauri — фреймворк для десктоп-приложений, которые выглядят как
веб-страница, но физически состоят из двух РАЗНЫХ процессов,
работающих рядом.

## Два процесса в одном приложении

1. **Фронтенд** — вебвью (встроенный движок браузера конкретной ОС:
   на Linux это WebKitGTK, системный компонент, НЕ Chrome и не
   отдельный скачанный браузер) отрисовывает твой React-интерфейс —
   ровно тот же код, который Vite собирал бы и для обычного сайта.
2. **Бэкенд** — обычный скомпилированный Rust-бинарник. Он открывает
   системное окно, встраивает в него вебвью и предоставляет
   фронтенду "команды", которые тот не может выполнить сам:
   чтение/запись файлов, доступ к SQLite, сетевые запросы с явными
   правами (ниже).

Это принципиально отличается от обычного сайта в браузере: там
JS-код НЕ имеет доступа к файловой системе вообще (из соображений
безопасности). В Tauri — доступ есть, но только через явно
объявленные "команды" на Rust-стороне, а не напрямую.

## `#[tauri::command]` и `invoke()` — граница между процессами

Rust-сторона объявляет функцию, доступную фронтенду:

```rust
// src-tauri/src/lib.rs:33
#[tauri::command]
fn get_db_url(state: tauri::State<'_, VaultState>) -> String {
    state.db_url.clone()
}
```

`#[tauri::command]` — атрибут (похож на декоратор), который говорит
Tauri "сделай эту функцию вызываемой с фронтенда". Дальше она
регистрируется в списке разрешённых команд:

```rust
// src-tauri/src/lib.rs:208 (фрагмент)
.invoke_handler(tauri::generate_handler![
    read_file_bytes,
    get_db_url,
    set_vault_path,
    // ... остальные команды
])
```

Фронтенд вызывает её через `invoke()` из пакета `@tauri-apps/api`:

```ts
// src/features/data/DataScreen.tsx:97
import { invoke } from "@tauri-apps/api/core";

invoke<string>("get_db_url").then((url) => setVaultPath(vaultFolderFromDbUrl(url)));
```

`invoke<string>("get_db_url")` — "вызови Rust-команду по имени
`get_db_url`, жду строку в ответ". Имя передаётся строкой (не прямым
вызовом функции — связь по имени, компилятор TS не проверяет, что
такая Rust-команда существует, это проверяется только в рантайме).
`invoke()` всегда возвращает `Promise` (глава 03) — вызов уходит в
другой процесс, результат не мгновенный.

Для команд с параметрами — второй аргумент, объект с именами полей,
совпадающими с именами параметров Rust-функции:

```rust
// src-tauri/src/lib.rs:42
#[tauri::command]
fn set_vault_path(path: String) -> Result<(), String> {
    let path = PathBuf::from(path);
    if !path.is_dir() {
        return Err("not a directory".into());
    }
    vault::write_pointer(&path);
    Ok(())
}
```

```ts
await invoke("set_vault_path", { path: someChosenFolder });
```

`Result<(), String>` в Rust — "либо успех без значения, либо строка с
описанием ошибки" (Rust-эквивалент try/catch — Rust не бросает
исключения, а возвращает значение, явно говорящее об успехе/провале).
Если Rust вернул `Err(...)`, на стороне TS `await invoke(...)` упадёт
с исключением — значит, его тоже нужно оборачивать в `try`/`catch`
(глава 03), иначе ошибка молча потеряется точно так же, как в баге
из главы 03.

## Почему не вызвать SQL прямо из TS?

Потому что у вебвью нет доступа к файловой системе. Вместо отдельных
`#[tauri::command]` на каждый SQL-запрос в проекте используется
плагин `tauri-plugin-sql` — он сам предоставляет frontend-API
(`db.select(...)`, `db.execute(...)`, которые ты уже видел в главе 07)
и сам отправляет запросы через границу `invoke` за кулисами, так что
отдельную Rust-команду под каждый SQL-запрос писать не нужно.

## Права доступа (capabilities) — офлайн-first по умолчанию

Tauri требует ЯВНО разрешить, какие возможности доступны фронтенду —
по умолчанию запрещено почти всё:

```json
// src-tauri/capabilities/default.json (реальный, целиком)
{
  "identifier": "default",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "core:window:allow-close",
    "sql:default",
    "sql:allow-execute",
    "dialog:default",
    "opener:default",
    {
      "identifier": "http:default",
      "allow": [{ "url": "https://kase.kz/*" }]
    }
  ]
}
```

- `"sql:default"`, `"sql:allow-execute"` — разрешён доступ к SQLite
  через плагин.
- `"dialog:default"` — разрешены системные диалоги (выбрать файл/папку).
- `"opener:default"` — разрешено открыть файл/папку в системном
  файловом менеджере.
- Блок `"http:default"` с `"allow": [{ "url": "https://kase.kz/*" }]`
  — это **единственное** исключение из полностью офлайн-работы
  приложения: разрешён HTTP-запрос, но ТОЛЬКО на домен `kase.kz`
  (биржа, откуда подтягиваются цены акций для модуля инвестиций).
  Запрос на любой другой домен с фронтенда просто не пройдёт — это
  проверяется на уровне Tauri, а не доверяется коду приложения.

Без строки про `kase.kz` в этом файле JS-код мог бы написать
`fetch("https://kase.kz/...")`  сколько угодно раз — запрос был бы
заблокирован ещё до выхода из вебвью.

## Два процесса при разработке (`npm run tauri dev`)

Как уже было в главе 04: Tauri CLI запускает Vite (фронтенд,
`localhost:1420`) и параллельно собирает и запускает Rust-бинарник
(`cargo run`), который открывает окно, смотрящее на тот же
`localhost:1420`. В собранном приложении (`tauri build`) Vite уже не
нужен — вся фронтенд-сборка (из `dist/`) встраивается прямо в
бинарник, и окно грузит её из самого приложения, без какого-либо
сервера, даже локального.
