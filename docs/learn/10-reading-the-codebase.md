# 10. Как теперь находить нужный код самому

Последняя глава — не новые концепции, а практические привычки: как
по симптому ("не работает кнопка X", "хочу понять, как считается Y")
быстро найти нужный файл в этом конкретном проекте, и что делать
дальше — с `SKELETON.md`.

## От клика на экране до файла

1. **Какая это вкладка?** — смотри таблицу в главе 09: по вкладке
   понятно, в какой папке `features/` искать экран.
2. **Какой это экран внутри вкладки?** — у каждого Hub-компонента
   (`FilesHubScreen`, `OperationsHubScreen`, `AnalyticsHubScreen`)
   секции явно перечислены в самом файле (`src/features/.../...HubScreen.tsx`)
   — там видно, какой компонент отвечает за какую секцию.
3. **Какая кнопка/поле конкретно?** — в файле экрана (например
   `FilesScreen.tsx`) ищи текст кнопки (`grep -n "Удалить"
   src/features/files/*.tsx`) — у React нет "скрытой" логики, обработчик
   всегда рядом с самим JSX-элементом (`onClick={...}`).
4. **Куда ведёт обработчик?** — если это простая функция в том же
   файле — читай её тело. Если она дёргает что-то из `db/` — переходи
   туда по импорту в начале файла (`import { deleteStatement } from
   "../../db/statements"`).

## От названия функции к файлу

Папки в `src/` named по смыслу, не по типу файла — так что лучше
grep, чем угадывание:

```bash
grep -rn "export function deleteStatement" src/
grep -rn "export async function deleteStatement" src/
```

(функция может быть `function` или `async function` — если не
уверен, грепай без `async`, но с `export`, чтобы не находить вызовы,
только объявление).

## Что проверять перед тем, как менять код

Этот проект держит три проверки, которые нужно гонять после любого
изменения (команды реальные, из `package.json`/обычных CLI):

```bash
npx tsc --noEmit     # проверка типов без сборки (глава 04)
npx vitest run       # все тесты из tests/
cargo check --manifest-path src-tauri/Cargo.toml  # Rust-сторона компилируется
```

Тесты в `tests/` повторяют структуру `src/` (`tests/db/statements.test.ts`
тестирует `src/db/statements.ts`) — если меняешь функцию, у неё почти
наверняка уже есть тест рядом, который можно запустить отдельно:

```bash
npx vitest run tests/db/statements.test.ts
```

## Откуда берётся состояние на экране — общая схема

```
Клик/ввод на экране
   │
   ▼
Обработчик в компоненте (onClick/onChange — глава 05)
   │
   ▼
Вызов функции из src/db/* (SQL-запрос) ИЛИ invoke() в Rust (глава 08)
   │
   ▼
await — компонент ждёт результат (глава 03)
   │
   ▼
setState(...) с новым результатом
   │
   ▼
React перерисовывает компонент с новыми данными (глава 05/06)
```

Любой "почему на экране не то, что я ожидал" почти всегда
разматывается именно в эту сторону: сначала — какой `useState`
отвечает за этот кусок экрана, потом — кто его обновляет
(`setXxx(...)`), потом — что именно туда пишут (результат какого
запроса).

## Переход к SKELETON.md

Теперь можно открыть [`SKELETON.md`](../../SKELETON.md) и читать его
не как список непонятных символов, а как справочник:

- Раздел **"Стек"** — таблица технологий; теперь понятно, зачем там
  каждая строка (Vite — глава 04, Tauri — глава 08, sqlx — глава 07).
- Раздел **"Модули и компоненты"** — за каждым названием папки стоит
  конкретная ответственность, и ты уже видел это в главе 09 на
  примере импорта.
- Раздел **"Функции и классы"** — сигнатуры вида `buildScreen(state): View`
  — после глав 01–03 это читается буквально: имя, типы параметров,
  тип возврата (возможно обёрнутый в `Promise`), и одна строка о
  смысле.
- Раздел **"Потоки данных"** — то же самое, что схема выше, но по
  каждому модулю отдельно.
- Раздел **"Документация для офлайна"** — там собраны конкретные
  команды/офлайн-инструменты (`cargo doc`, DevDocs и т.д.) для более
  глубокого погружения в конкретную технологию, если какой-то главы
  этого курса не хватило.
- Раздел **"Порядок сборки"** — чеклист, в каком порядке имеет смысл
  реализовывать модули, если бы ты собирал такой проект с нуля сам.

Дальше — обычная работа с любым чужим кодом: читать сверху вниз от
точки входа (`App.tsx`), следовать за импортами, запускать тесты,
проверять гипотезы через `grep`.
